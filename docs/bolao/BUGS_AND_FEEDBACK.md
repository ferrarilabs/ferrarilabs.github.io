Audit covered `app.js` (site) and `send_result_email.py` (cron email script) side by side. The site was clean throughout — everywhere (ranking, CSV/master export, admin's manual email builder) shares one `scoreEntry()` implementation, so it can't internally disagree with itself. The email script had drifted from it though, since it re-implements the scoring/bracket logic independently in Python:

- **Follow-up — the clock was still running through Portugal vs Croatia's actual halftime (Eduardo), same day:** v4.59's fix relied on recognizing ESPN's halftime status text, which couldn't be confirmed against the real live feed from this sandbox (no network access to ESPN) — in practice it didn't match, and separately, a concurrent session's v4.61 (monotonic clock, no backward jumps) made this worse by removing the old 150s safety cap, so a genuinely paused clock with no matching status text would now extrapolate forward forever with nothing to stop it. Tried fetching the actual official America250 logo (Wikimedia Commons has an SVG) to replace the CSS recreation entirely, but this sandbox's network policy blocks that host (403). - **Follow-up — "The logo is huge fix it this is horrible," with a photo of the actual live site (Eduardo):** the v4.71 fix looked correct in every test, and checking a clean, fully uncached load of the exact current `main` source confirmed the badge really does render at the intended small size — the deployed *source* was never broken. Real cause: a concurrent session pushed another commit (`021c1ae`, nav layout) about a minute after the badge fix merged, changing `styles.css` again but re-using the same `siteVersion` string ("v4.71") instead of bumping it — and `sync_version.yml` was scoped to only fire on `config.js` changes, so it never ran for that commit at all. `index.html`'s cache-busting `?v=` stayed frozen on a URL whose cached content no longer matched what a browser would need to load — that's what Eduardo's screenshot was actually showing. - **"Bug no relógio... já estamos no minuto 54 e é o segundo tempo então +11 não está correto," with a screenshot of Australia vs Egypt showing "55:11 (+11)" (Eduardo):** real bug, confirmed. `formatMatchClock` had no upper limit on how far past a half boundary (45/90/105/120 min) it would still call the extra time "stoppage" — since ESPN's clock is one continuous counter with no built-in sense of "which half," a value like 55:11 (legitimately ~10 minutes into the 2nd half) kept reading as "45:00 plus 10 minutes of 1st-half stoppage" indefinitely, just because it was still numerically past 45. Fixed in v4.73 two ways: a realistic 8-minute cap on how long past any boundary something can still be called stoppage (beyond that, assume the half has changed and just show the plain clock), plus a more precise sticky per-match record — the moment the app directly observes the match paused (`isHalftime`) near a boundary, it remembers that boundary is behind us for good, so even resuming just 1–2 minutes later shows no false "(+N)" at all. Verified with Playwright reproducing the exact reported scores (55:11 → clean, no annotation) plus three regression cases (real 1st-half stoppage, resuming shortly after a confirmed halftime, real 2nd-half stoppage near 90) — all correct.

3. Send Eduardo the console output, browser/OS, and steps to reproduce via WhatsApp or email (emferrari@gmail.com).
