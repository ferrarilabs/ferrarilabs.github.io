ROOT CAUSES (round 2's two bugs)
---------------------------------
1. Subject: send.mjs sent template_params.subject, a key the EmailJS
   template (template_xq7yzzb) does not recognize. EmailJS silently falls
   back to its own dashboard-configured static Subject text ("Bolão do
   Ferrari - {{X}}") when an expected variable is missing — no error, no
   indication in the API response. Root-caused by comparing against
   scripts/send_result_email.py's send_email(), which sends the subject text
   under entry_name AND receipt_code (never subject) — confirmed working by
   finding a real, correctly-subjected past email in Gmail ("Bolão do
   Ferrari - Resultado Powerball — 01.08.2026 22:59 ET", sent 2026-08-04 by
   that script). Fixed: send.mjs now sends the same canonical subject value
   under entry_name, receipt_code, AND email_subject (defensive third key —
   see send.mjs's "SUBJECT CONTRACT" comment for the full reasoning and
   honest limitation: this codebase has no credential to inspect/edit the
   EmailJS dashboard directly).
2. A second, related bug found via the same real-inbox cross-check: EmailJS
   HTML-escapes subject template variables server-side, so "/" arrived as
   the literal text "&#x2F;" (e.g. "05&#x2F;08&#x2F;2026"). Fixed with
   render.mjs's subjectSafeDate() — subject lines use "." instead of "/" in
   dates, matching send_result_email.py's own documented workaround for the
   exact same issue.
3. Ticket numbers: the HTML row relied entirely on inline CSS (margin) for
   visual separation between number spans, with zero literal-text fallback —
   when the delivered email's styling didn't fully survive, digits appeared
   concatenated. Fixed: every number is its own table cell, a literal "·"
   separator sits in its own cell between them, the Powerball number gets an
   explicit "| Powerball:" text label (never a bare colored digit), and a
   fully redundant plain-text line ("24 · 31 · 47 · 52 · 63 | Powerball: 17
   | Power Play: Sim") is included under the visual row.
